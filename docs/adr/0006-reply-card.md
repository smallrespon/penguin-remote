# Run 回复承载：文本消息 → 交互卡片

Run 的占位消息、流式预览与定稿从文本消息整体切换为飞书交互卡片（Card 2.0）：预览与定稿都经 lark-cli `im messages patch` 更新同一张卡片，每个工具调用渲染成一个默认收起的 `collapsible_panel`，思考只留一行标签，正文永远展开，状态文案放卡片 header，用量行放页脚。动因是用户原话：「工具调用和思考过程可以折叠吗，像 zcode 一样，工具调用太长了」——工具轨迹在文本消息里只能平铺，长 Run 会把答案冲得看不见。设计参照 ZCode 的有序 parts 模型与折叠交互（调研见 `docs/research/zcode-reply-structure.md`）：parts 的顺序、分区语义与截断口径全部沿用，变的只是承载。

**Status**: accepted (2026-10-22)

**背景（飞书能力事实，均已实测）**：文本消息单条编辑上限 20 次（第 21 次报 `230072`），长任务必然撞上；`im messages patch` 更新卡片没有这条上限（连打 27 次全过），但单次 patch 内容上限 30KB、单卡最多 200 个元素，且客户端需 ≥7.20 才能完整渲染（更旧的客户端只显示卡片 header）。另：`tool_call_output` 事件不带错误字段，单工具错误标记不可行，Run 级失败照旧在页脚呈现。

**决策**：

- 占位 / 预览 / 定稿三态全部走卡片：占位即建卡，预览与定稿都 patch 同一张卡，不再换新消息续接。
- 卡片 header 只放状态文案：占位「🦐 思考中…」、预览「🦐 执行中…」、定稿完成「✅ 完成」、定稿失败「❌ 未正常完成」。
- 每个工具调用 = 一个默认收起的 `collapsible_panel`：标题行「🔧 名称 · 截断参数」，点开展示参数与 output；output 保留末尾 8 行、每行 ≤100 字符，超出显式标注「已截断，共 N 行」。
- 思考保持一行标签「🧠 思考 · N 字 · X.Xs」（12px notation 字号）：不存全文、不进面板——「思考可折叠」这个诉求用一行标签即可满足。
- 正文永远展开，不进面板；审批与压缩提示保持普通行。
- 定稿页脚 = 分割线 + 用量行，文案与旧文本版一致。
- 超限策略沿用旧文本版的「中间省略 N 个分区」，另加约 20KB 的预算上限，防撞 patch 的 30KB 内容上限与 200 元素上限。
- 降级：卡片发送或 patch 失败时退回原有文本降级链路，文本渲染路径保留为兜底，不删除。
- 边界：非 Run 消息（`/status`、`/help`、错误提示、忙提示等命令响应）保持文本消息，不走卡片。

**Consequences**: 长 Run 的工具轨迹收进可折叠面板，消息体量不再随工具调用数线性增长，预览 / 定稿同卡更新也不再受 20 次编辑上限约束。代价与风险：卡片 JSON 生成取代纯文本拼接，大小预算（约 20KB 自设 / 30KB patch 上限 / 200 元素上限）成为渲染层的新约束；每次 patch 重建卡片内容，用户手动展开的面板可能被重置回收起态；旧客户端（<7.20）只能看到 header，内容不可见；文本渲染路径作为兜底与卡片双轨并存，两边的渲染口径需要同步维护。

**Considered Options**:
- 仅定稿用卡片、预览仍是文本：预览阶段依旧逐次 `messages-edit`、依旧撞 20 次上限，而「工具太长」的痛点主要发生在执行过程中；定稿时还要从文本跳成卡片，状态割裂。放弃。
- 不引入卡片，只加强文本截断（如合并连续同类工具调用）：截断给不了「想看时再看」，与用户「像 zcode 一样可以折叠」的明确诉求不符。放弃。
